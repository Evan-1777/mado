## 1. 背景与目标

用户反馈：双击启动 Mado 时，窗口先呈现一瞬间黑色/空壳，随后界面才渲染出来。上一阶段（.docs/10-25-v1）为压缩首屏时间，把窗口可见时机与编辑器 bundle 解耦：`load` 事件后 Wails 显示窗口，而 `app.js` 由启动脚本在 `load` 之后才注入执行。其代价是窗口先露出静态骨架（titlebar + 空 toolbar + 空 pane），约 115ms 后才被真实 UI 替换。

本次目标是让窗口的**第一个可见帧就是真实界面**：

- 不再出现黑色/空壳/白闪等中间帧；
- 持久化主题（深色或浅色）在窗口可见前已应用；
- 编辑器、工具栏、标题栏在可见时已构建完成；
- 不改变启动文件打开、设置读取与预览按需渲染的既有语义。

### 非目标

- 改变 WebView2 冷启动与用户数据目录初始化的系统侧成本。
- 再次拆包、懒加载 KaTeX 或调整 bundle 组成。
- 修改主题切换逻辑、设置持久化格式或窗口状态记忆。

## 2. 现状与根因

### 2.1 当前启动链路

1. Go 侧读取 `settings.json`，确定窗口尺寸、最大化与主题设置，随后 `wails.Run` 创建隐藏窗口并导航。
2. `index.html` 先绘制静态启动骨架；`head` 预加载 `app.js`；`load` 后由内联脚本注入并执行 bundle。
3. Wails 在 WebView2 navigationCompleted（约等于 `load`）时显示窗口，此时 bundle 尚未执行。
4. bundle 构建真实 titlebar/toolbar/pane 与 CodeMirror，`init` 并发拉取设置与启动文件，应用主题后才具备最终外观。

### 2.2 证据

- 上一阶段实测（远程 Chrome，同机本地服务）：FCP 44–45ms、编辑器就绪 160–165ms、预览 217–222ms。FCP 即骨架可见时刻，编辑器就绪即真实 UI 完成时刻，两者间隔约 115ms，正是用户感知到的"黑一瞬间"。
- `frontend/index.html` 的内联启动背景为 `#09090b` 且根节点写死 `data-theme="dark"`，均为 2026-09-09 Fluent 重构前的 Zinc 遗留值；真实深色帧背景为 `#202020`、编辑区为 `#1f1f1f`。启动期颜色与最终主题不一致。
- Go 侧 `BackgroundColour` 为 `#0f1117`（近黑），同时作为窗口画刷与 WebView2 默认背景；在首帧合成前可见。
- 持久化主题只有 Go 侧在窗口创建前可知；前端要等 bundle 执行后经 `GetSettings` IPC 才能获知。骨架阶段不可能正确呈现浅色主题。

### 2.3 根因

窗口可见时机被前移到"真实 UI 尚不存在"的阶段，而该阶段的画面是不带按钮、不带编辑器、且与持久主题无关的空壳。颜色修正只能减轻、不能消除这段空壳期；正确的结构约束是：**窗口可见性必须与真实 UI 就绪耦合**。

## 3. 方案与阶段划分

采用 Wails 规范的 `StartHidden: true`：窗口创建后保持隐藏，由前端在真实 UI 构建完成、持久主题应用、页面 `load` 完成后调用 `WindowShow()` 显示。此时 Wails 已完成 WebView2 的首次合成，窗口出现即完整界面。

| 项目 | 内容 |

## 4. 架构决策

| 决策项 | 选择 | 理由 | 替代方案（为何不选） |
|--------|------|------|----------------------|
| 窗口显示 | `StartHidden: true` + 前端在界面就绪后 `WindowShow()` | 唯一能让"第一可见帧 = 真实 UI"的机制；主题、编辑器、外壳均已就绪；Wails 官方启动模式 | 保留骨架并修正配色（仍是空壳，未解决"随后才渲染"）；仅恢复同步 bundle（主题仍可能滞后一帧，浅色主题存在暗闪窗口） |
| 显示时机 | 应用设置并等待 `load` 后显示，先于启动文件加载 | 主题与外壳就绪即可见；不被文件读取与大文档渲染阻塞 | `init` 全完成后显示（大文档延长不可见时间，收益仅是内容不弹入）；`load` 前显示（WebView2 首帧未合成） |
| 主题一致性 | 沿用前端 `applyTheme`，显示前置完成 | 主题逻辑保持单一来源，不新增 Go→HTML 注入通道 | 资源中间件改写 index.html 注入主题（多一层服务端 HTML 改写，且不解决空壳期） |
| 启动骨架 | 退役 | 窗口在界面就绪前不可见，骨架永远不会被看到；保留即死代码与双份结构维护 | 保留骨架（不可见、无收益） |
| bundle 加载 | 恢复常规同步脚本，删除 preload 与 load 后注入 | 窗口可见性已由 `WindowShow` 控制，延迟注入失去意义；结构更少 | 保留延迟注入（多一次事件循环与引导脚本，无可见收益） |
| 启动文件 | 显示窗口后再加载 | 保证窗口出现不被磁盘读取与预览渲染阻塞；内容稍后自然填入 | 先加载再显示（打开大文档时不可见时间不可控） |

## 5. 风险清单

| 风险 | 等级 | 缓解措施 |
|------|------|----------|
| 前端未调用 `WindowShow` 导致窗口永不显示 | 🔴 高 | 显示调用位于设置 try/catch 之后，路径无未捕获异常；uiContract 同时锁定 Go 的 `StartHidden` 与 TS 的 `WindowShow`；startup.check 断言恰好调用一次且晚于设置应用 |
| `WindowShow` 早于 Wails navigationCompleted 的 WebView2 hide/show 处理 | 🟡 中 | 显示前等待 `load` 事件，确保导航完成且首帧可合成；Wails 的控制器切换在同一主线程调用内完成，不产生中间帧 |
| 隐藏窗口下 CodeMirror 几何或焦点异常 | 🟡 中 | 窗口以目标尺寸创建，WebView2 控制器同步 Resize；既有窗口 resize 与 `cm.requestMeasure()` 路径不变；显示后仍执行 `cm.focus()` |
| 三项无头检查的运行时桩缺少 `WindowShow` | 🟡 中 | 三个 check 的 `window.runtime` 桩统一补 `WindowShow`，否则 init 会在调用处抛错 |
| 本机无法复现 Windows/WebView2 的实际首帧 | 🟡 中 | 本地验证 DOM/时序契约与构建；结构性保证（窗口隐藏直到前端显示）由契约测试锁定，最终视觉由用户在 Windows 端确认 |
| 时间线回退被误读为性能退化 | 🟢 低 | 明确取舍：窗口可见从约 45ms 后移到 bundle + IPC（约 160–200ms），仍早于优化前 420ms 基线；换取无中间帧 |
