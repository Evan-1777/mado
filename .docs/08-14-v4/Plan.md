## 1. 背景与目标

用户报告三个问题：

1. 通过 Windows「打开方式」用本应用打开 .md 文件，应用仍显示上次打开的文档，而非用户指定的文件。
2. 未保存关闭弹窗点击确认按钮后程序无法退出。
3. 弹窗逻辑需要重设计：「是否保存该文件的修改」——「是」=保存并关闭，「否」=关闭不保存，点 X =不关闭不保存。

### 根因分析

| 问题 | 根因 |
|------|------|
| 打开仍显示旧文档 | Windows 文件关联以命令行参数传入文件路径，但后端从未解析启动参数；前端启动流程固定加载上次打开的文件 |
| 点确认关不掉 | 自定义关闭按钮确认后调用退出，退出又触发窗口关闭前回调，回调内再次弹窗，且第二个弹窗默认按钮是「取消」，用户按回车即取消，表现为「点是无法关闭」 |
| 弹窗语义 | 当前弹窗只有「关闭/取消」两键，无法表达「保存/不保存/取消」三态；且保存需要编辑器内容，内容仅存在于前端，同步的后端回调无法完成保存动作 |

## 3. 架构决策

| 决策项 | 选择 | 理由 | 替代方案（为何不选） |
|--------|------|------|----------------------|
| 关闭确认的处理位置 | 后端发事件→前端统一处理 | 保存需要编辑器内容（仅前端持有），窗口关闭前回调是同步的无法等待前端；原生模态对话框阻塞 UI 消息循环，天然防重入 | 后端持久化编辑器内容（每击键 IPC，浪费）；纯前端确认（Alt+F4 走不到前端） |
| 防止二次弹窗 | `quitting` 标志 | 确认后强制退出前置标志，关闭前回调见标志直接放行 | 计数器/延时（不可靠） |
| 弹窗三态 | 三按钮 + CancelButton 承接 X/Esc | 对话框 API 中 X 和 Esc 固定返回 CancelButton 指定的按钮，天然实现「叉掉=取消」 | 两按钮（无法区分「否」与「取消」） |
| 未命名文件点「是」 | 另存对话框 | 无路径无法落盘；取消另存则留在应用不丢内容 | 静默不保存（丢数据）；直接退出（丢数据） |
| 启动参数 | 只在启动时解析一次，校验交给加载流程 | 最小实现；加载失败自然回退到欢迎文档 | 启动时预读文件内容（前端反正要读，重复） |

## 4. 风险清单

| 风险 | 等级 | 缓解措施 |
|------|------|----------|
| 生成绑定副本未同步导致 CI 语法检查失败 | 🟡 中 | 按 Project.md 约定手动同步 App.js/App.d.ts，CI 生成版本以后端为准 |
| 多实例：应用已运行时再双击文件会开第二个实例 | 🟢 低 | 本次不处理（用户未报告）；记录为已知限制 |
| 保存失败时用户预期退出却留在应用 | 🟡 低 | 保存失败不退出，状态栏提示 Save failed，用户可重试或另存——宁可留下也不丢数据 |
| X/Esc 行为依赖对话框 API 的 CancelButton 语义 | 🟢 低 | 该语义在现有弹窗中已被使用（Cancel 按钮即承接），行为一致 |
