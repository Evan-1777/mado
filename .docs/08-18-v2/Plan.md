**版本**：v1.0  
**回归测试结论**：前端 esbuild 语法检查、npm run build 生产构建通过，Go vet 及 4 个包全部单元测试 PASS，无回归问题。

## 1. 背景与目标

在 Windows 无边框窗口（Frameless）模式下，先前方案已修复底部边缘缩放，但**右侧边缘与右下角依然无法拉动窗口大小**。
经深度调用链路排查，根本原因包括：
1. **原生滚动条阻断 DOM 事件**：右侧与右下角为预览 iframe 及编辑器的垂直滚动条区域（宽度约 15~17px）。Chromium 将原生滚动条作为合成器/系统级控件处理，鼠标移入时不向 DOM 分发 `mousemove`/`mousedown`，并在接近边缘时触发 `mouseleave`，导致视口边缘检测彻底失效。
2. **Wails 内部运行时冲突与光标覆写**：Wails 底层注入的 `main.js` 基于带有系统不可见边框偏差的 `outerWidth` 进行边缘计算，且在导航完成后被强制重新开启，持续覆写 `document.documentElement.style.cursor` 并重置缩放状态。

本次计划通过**顶层绝对穿透把手系统 + Wails 内部运行时严格冻结 + 全状态窗口联动**进行深度彻底修复，达成以下目标：
- 窗口 8 方向（上、下、左、右、左上、右上、左下、右下）全边缘与全边角在任何内容、模式（Split / Editor / Preview）下均能瞬时显示正确调整光标并精准触发 Win32 原生缩放。
- 彻底解决 iframe 与编辑器滚动条对右边缘/右下角的事件吞没。
- 最大化状态下自动隐藏边缘把手，确保 Win11 标题栏右上角关闭按钮热区行为完全符合系统规范。

## 3. 架构决策

| 决策项 | 选择 | 理由 | 替代方案（为何不选） |
|--------|------|------|----------------------|
| 边缘交互机制 | 顶层专用透明把手层（8 方向 Fixed Overlay） | 摆脱 DOM 坐标计算与 iframe 滚动条对事件的吞没，浏览器原生 CSS 光标零延迟渲染，`mousedown` 捕获率 100% | 纯坐标计算监听（被原生滚动条吞没）；修改 Go 内部 Wails 源码（破坏第三方模块独立性） |
| 运行时冲突治理 | `Object.defineProperty` 冻结不可变属性 | 彻底防止 Wails 内部脚本在 `navigationCompleted` 后重置标志或覆写光标 | 仅在 init 时赋值（会被 Wails 后续执行的脚本覆盖） |
| 响应区域度量 | 边缘 6px、四角 10px×10px | 兼顾命中宽容度与内部内容（如滚动条、按钮）的正常操作空间 | 更宽把手（影响滚动条点击）；更窄把手（难以精准抓取） |
