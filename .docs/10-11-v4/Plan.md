## 1. 背景与目标

既有实现依赖浏览器沙箱 iframe 调用 `window.print()` / 系统打印管理器。在 Windows Edge WebView2 运行时中，离屏沙箱调用系统打印存在宿主窗口与 Chromium 模态限制，导致打印请求被直接丢弃，无任何系统窗口唤起（用户实机复现“仍无法导出、无任何弹窗”）。

根据用户最新明确授权（"不要用原生方案了，自己写吧"），本次计划彻底退役不可控的浏览器原生打印调用机制，转为端到端自研的独立 PDF 导出与持久化链路：

- **核心立论：复用已实证的 `SaveFileDialog` 通道**：既有文件保存逻辑（`main.ts:950`）中调用的 Wails 原生 `SaveFileDialog` 已在 Windows 目标环境中实证 100% 可用且交互确定。新方案将文件导出收敛至此通道，从结构根源消除“无任何弹窗”的黑盒风险。
- **完备的容器样式与字体注入**：为导出容器注入完整的动态主题 CSS（`cssForTheme()`）、KaTeX 样式表与公式回填，等待父上下文 `document.fonts.ready` 就绪后再执行捕获，坚决杜绝“无排版/公式乱码/字体缺失”问题。
- **按页分块高保真捕获**：在前端捕获渲染完毕的 Markdown DOM，按 A4 纸张几何比例逐页分块渲染，规避 Chromium 16384px 单 Canvas 硬件尺寸上限，支持任意超长多页文档，并在顶层子元素几何下沿软断页，重建每页一致内边距。
- **极简自研 PDF 1.4 包装器**：采用纯 TypeScript 实现符合 PDF 1.4 规范的轻量编码器（< 100 行），将多页图像封装为标准 PDF 格式，零 30MB+ 外部 PDF 库运行时负担。
- **死代码与契约清理**：同步清理 `base.css` 中废弃的 `@media print` 样式、变量及离屏沙箱 iframe 遗留代码，刷新测试断言与项目事实文档。

## 3. 架构决策

| 决策项 | 选择 | 理由 | 替代方案（为何不选） |
|--------|------|------|----------------------|
| 弹窗调起与可靠性立论 | 复用已验证的 Wails 原生 `SaveFileDialog` | 既有文档保存流程（`main.ts:950`）已证明该通道在目标 Windows 环境下 100% 确定能调起系统原生弹窗，彻底摆脱不可控的 `window.print()` | 继续调试系统打印预览（平台黑盒阻断，用户已明确否决）；网页端模拟 `<a>` 标签下载（非桌面原生体验） |
| DOM 栅格化工具 | 引入 `html2canvas`（约 3MB 解包，生产打包约 200KB） | 成熟稳定，能高保真解析父级继承的复杂 CSS 规则、自定义属性及 KaTeX span 排版；避免跨域与字体污化 | 原生 SVG `foreignObject` 截图（Chromium 在存在外部字体或样式时会将 Canvas 视作 tainted，导出图像直接抛错安全异常）；纯后端 HTML-to-PDF（后端缺乏浏览器排版与 KaTeX 渲染能力） |
| PDF 结构生成机制 | 前端按页分块捕获 + 极简自研 PDF 1.4 包装器 | 纯原生 TypeScript 组装标准 PDF 字典与图像流（< 100 行）；零 30MB+ 外部 PDF 库运行时负担；高保真还原样式 | 引入 `jspdf`（解包体积超 30MB，且中文字体需额外加载 15MB+ 字体包，严重违背 SCOPE 极简基线） |
| 文本层与矢量性权衡（Trade-off） | 接受位图页面呈现，优先保证排版绝对还原度与离线自包含 | 个人桌面 Markdown 编辑器场景下，公式排版美观度、语法高亮与中文字体自包含渲染为首要诉求；自研位图打包无需引入大型 CJK 矢量字体引擎（15MB+），在轻量与保真间取得平衡 | 内嵌 CJK 矢量字体库与重型排版引擎（严重违背 SCOPE.md 极简与轻占用原则） |
| 画布渲染机制 | 按 A4 页面窗口分块独立渲染 | 彻底规避单张 Canvas 超大尺寸导致的 Chromium 16384px / 2.68 亿像素硬上限崩溃；使得每页内页边距能够确定性独立重建 | 单张全文档一次性渲染后纵向切片（超 15-20 页长文档会静默产生空白崩溃） |
| 废弃打印样式处理 | 彻底移除 `base.css` 的 `@media print` 块与相关变量 | 遵循工程纪律，新管线不走系统打印，消除死代码与维护歧义 | 保留废弃打印规则（遗留死代码与测试断言冲突） |

## 4. 风险清单

| 风险 | 等级 | 缓解措施 |
|------|------|----------|
| 实机验收盲区：本地 Linux 环境无法全真检验 WebView2 下渲染与导出行为 | 🔴 高 | 严格定义职责边界：Linux 环境通过契约测试、语法检查与单元测试守住代码逻辑与 PDF 规范结构；物理 PDF 视觉与分块效果明确交由 Windows 端按清单手动验收 |
| 离屏容器未正确加载样式与字体导致捕获空白或公式乱码 | 🟡 中 | 明确严格的时序依赖：注入 `cssForTheme()` + KaTeX 资源 → 调用 `renderMathInFrame` 回填公式 → `await document.fonts.ready` 确保字体栅格化完毕再启动捕获 |
| 超长文档连续捕获导致内存峰值 | 🟡 中 | 逐页捕获后及时释放对应 Canvas 内存，限制最大设备像素比（DPI ≤ 2） |
| 无 `data-line` 锚点的块导致分页切字 | 🟡 中 | 遍历容器所有直接子元素（`article.children`），无锚点块退化为真实几何 `getBoundingClientRect()` 下沿软避让 |
| 另存为对话框被用户主动取消 | 🟢 低 | 后端在路径为空时返回安全标记，前端捕获后静默退出并恢复导出按钮状态，不显示错误红字 |
