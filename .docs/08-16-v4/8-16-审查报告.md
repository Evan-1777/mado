## 结论摘要

- **架构**：分层清楚，`internal/*` 禁止互相依赖，App 绑定层是唯一聚合点；适合当前单窗口编辑器规模。当前主要架构风险是 Wails 全量依赖链较重、`internal/filesys` 与 `internal/settings` 通过共享 JSON 文件松耦合，以及多实例限制。
- **代码质量**：整体可读性好，注释解释了关键踩坑；单元测试覆盖 4 个内部包，当前全部通过。发现 1 处实际缺陷：`slugIDs.Generate` 在重复标题场景对同一输入反复调用 `slugify`，复杂度为 O(n²)，2000 个重复标题时渲染耗时约 0.6s。本次为 Brainstorm 审查，未修改代码。
- **性能**：渲染器每击键新建 goldmark 引擎与高亮器，100~500 段文档可接受，但代码块使 Chroma 高亮成本放大，500 段含代码文档单次渲染约 31ms、分配约 11.8 MB；重复标题是主要退化点。内存占用属轻量（前端 bundle 527 KB、node_modules 16 MB、dist 544 KB）。

## 一、架构审核

### 1.1 模块划分

```text
main.go ── wails.Run
  │
  └── app.go (App 绑定层：唯一允许 import internal 的包)
        ├── internal/filesys   文件 I/O、lastfile 持久化
        ├── internal/mdrender  goldmark 渲染 + script 剥离 + slug IDs
        ├── internal/settings  主题偏好持久化
        └── internal/theme     CSS 组合（go:embed 内嵌）

frontend/src/main.ts ── CodeMirror 6 + 预览 iframe
        └── frontend/wailsjs   自动生成绑定
```

架构符合项目定位：`internal/*` 互相不依赖，`filesys` 与 `settings` 通过共享 `settings.json` 的顶层字段松耦合，避免引入数据层。前端没有框架，状态集中在 `main.ts`，对单窗口双栏应用是合理选择。

### 1.2 已识别架构风险

| 风险 | 影响 | 建议 |
|---|---|---|
| `settings.json` 由 filesys/settings 两个包各自读写，无锁、无原子写 | 极端情况下并发写可能互相覆盖；当前单用户低频操作风险低 | 维持现状可接受；若增加设置项，可收敛到单一 storage 包 |
| `filesys.SetLastFile` 与 `settings.Save` 各自先读后写，共享文件存在 read-modify-write 竞争窗口 | 保存文件 + 切换主题同时发生可能丢一个字段 | 短期可接受；后续可加文件锁或单写者 |
| 未启用 Wails SingleInstance | 双击关联文件会启动第二个实例，与 `SetStartupFile` 的「打开方式」设计冲突 | 需要时启用 `SingleInstanceLock` + `OnSecondInstanceLaunch` |
| Go 侧 App 字段（`dirty`、`quitting`、`settings`）无同步原语 | Wails 绑定调用通常在主线程，当前单窗口场景风险低；但 `SetDirty` 和 `OnBeforeClose` 若并发则存在数据竞争 | 若未来加后台任务/多窗口，需加 mutex 或 atomic |
| 渲染引擎每次调用都新建 | goldmark 非并发安全，当前单线程编辑场景成本约 27µs，可接受 | 保持现状，避免为省这点成本引入并发复杂度 |

## 二、代码质量审核

### 2.1 发现的实际缺陷（未修改）

`internal/mdrender/mdrender.go` 的 `slugIDs.Generate` 当前实现：

```go
id := slugify(value)
for i := 1; s.seen[id]; i++ {
    id = fmt.Sprintf("%s-%d", slugify(value), i)  // 每次重复都重新 slugify
}
```

- **问题**：同一个标题出现 N 次时，第 N 次冲突会对同一输入重复执行 `slugify` N 次，总体为 O(n²)。实测 2000 个相同标题渲染耗时约 0.6s、分配约 131 MB。
- **建议修复**：循环前计算一次 `base := slugify(value)`，循环内只做 `fmt.Sprintf("%s-%d", base, i)`。行为不变，仍生成 `foo`、`foo-1`、`foo-2`。
- **影响**：真实文档通常不会有大量完全相同的标题，因此该缺陷不是当前版本的主要瓶颈；但修复成本低，建议下次代码变更时一并处理。

当前重复标题基准（500 个相同标题，10 次迭代）：

| 指标 | 值 |
|---|---|
| 单次渲染 | 37.2 ms |
| 分配 | 7.98 MB |
| 分配次数 | 533,702 |

### 2.2 其他代码质量观察

**优点**
- 注释质量高，`.docs/Project.md` 记录了所有已知坑与决策理由，代码注释能解释「为什么」。
- 内部包边界严格，测试不依赖 GUI，`go test ./...` 在 Linux 可完整运行。
- 前端状态流清晰：`renderVersion` 防乱序响应、`dirty` edge-triggered 同步、`closePending` 防重入。

**可改进项（低优先级）**
- `frontend/src/main.ts` 的 `lastRenderAt` 只写不读，`THROTTLE_MS` 没有实际作用；当前 debounce 逻辑仍可用，但注释声称的「100ms debounce + 80ms 节流」与实现不完全一致。
- `mdrender.StripScripts` 是未使用的导出函数，且实现只是把 `<script` 替换为 `&lt;script`，与 `Render` 内的正则剥离行为不一致；建议删除或统一。
- `frontend/package.json.md5` 是历史遗留文件，仓库中无任何读取方；建议在下次清理时移除。
- `app.go` 中 `OpenFileDialog` / `SaveFileDialog` 把取消映射为 `os.ErrNotExist`（Open 路径）或空字符串（Save 路径），两处取消语义不统一；前端已按空字符串处理，暂不影响。
- `docs/README.md` 为空文件，若无需用户文档可删除。

## 三、性能占用审核

### 3.1 实测环境

- CPU：AMD Ryzen 5 5600
- Go：1.25.3 linux/amd64
- 测试：临时 benchmark，仅测 `mdrender.Render` 单次调用，未计入 IPC 与 DOM 更新

### 3.2 渲染基准

文档样本：`## Section N ...` + 一段文本，可选每 2 段插入一个 `go` 代码块。

| 样本 | 单次耗时 | 吞吐 | 内存分配 | 分配次数 |
|---|---|---|---|---|
| 100 段，无代码块 | 0.68 ms | 16.3 MB/s | 511 KB | 2,676 |
| 100 段，50 个代码块 | 5.87 ms | 2.1 MB/s | 2.34 MB | 53,088 |
| 500 段，无代码块 | 3.27 ms | 17.1 MB/s | 2.42 MB | 12,291 |
| 500 段，250 个代码块 | 31.2 ms | 2.0 MB/s | 11.8 MB | 264,337 |
| 2000 段，无代码块 | 13.6 ms | 16.5 MB/s | 9.55 MB | 48,318 |

结论：

- 无代码块的普通 Markdown 文档在 100~2000 段范围内接近线性，单次 13.6ms，配合 100ms 防抖，打字体验可接受。
- Chroma 代码高亮是主要放大项：100 段含代码比无代码慢约 8.6 倍，500 段含代码约 31ms。500 段以上含大量代码块的文档，实时预览会出现可感知延迟。
- 每次渲染分配大量临时对象（500 段含代码约 11.8 MB），频繁打字时 GC 压力上升，但单窗口场景仍在可控范围。

### 3.3 体积与内存占用

| 项目 | 数值 |
|---|---|
| 前端 bundle（`dist/app.js`，minify） | 527 KB |
| 前端 CSS | 7.3 KB |
| `frontend/node_modules` | 16 MB |
| `frontend/dist` | 544 KB |
| Go 模块总数（含间接） | 116 |
| 前端锁文件条目 | 50 |

Wails 的 Go 依赖链（WebView2 绑定、Echo、chroma 等）是体积主要来源，属于框架固定成本。项目自身源码约 2,086 行，前端 bundle 主要由 CodeMirror 6 贡献。

### 3.4 性能改进建议（按性价比排序）

1. **复用 goldmark 引擎与高亮器**：`Render` 每次调用都 `goldmark.New` + `highlighting.NewHighlighting`，实测 100 段无代码样本中引擎构造约占 27µs，占比不大；但复用需要处理 goldmark 非并发安全，建议仅在确有性能瓶颈时做。
2. **代码块高亮降级**：Chroma 高亮是最大耗时项。可对大文档关闭高亮、或只高亮首个代码块、或提供设置项切换。
3. **渲染防抖参数调优**：当前实现实际是 100ms 固定防抖（`THROTTLE_MS` 未生效）。若希望更跟手，可改为真正的 trailing debounce + throttle；若希望更省 CPU，可提高防抖到 150ms。
4. **前端目录解析轻量**：`parseToc` 是正则逐行解析，O(n)，对 2000 行文档无压力；无需优化。
